### s1-cell-rendertablefit (a0bcb37)

meant: aligned columns that survive a long value, spec.md:10.
did: `ui/utils/utils.go` — `Cell{Text, Color}` with `Cell.render`, `RenderTableFit`, `fitColumnWidths`. Weight 0 sizes to widest cell, weight >0 shares the remaining budget, last flexible column takes the rounding remainder so the table fills the width exactly. `RenderTable` untouched.
deviations: `Cell.Color` is a `color.Attribute`, not a `*color.Color` — an Attribute is what `utils.ColoredString` takes, so the precomputed-escape path is kept and no Color is allocated per cell; the zero value therefore has to mean "unstyled" (`color.Reset` as a cell style is meaningless) and is documented on the field. Validation is wider than the ticket asked: also errors on a weights slice that does not match the column count, and on a negative weight, because both would silently mis-lay-out every row. Degenerate case the ticket did not specify — when content-sized columns alone overrun the terminal, the budget is spent left to right and the trailing columns are squeezed to zero; chosen because the leftmost columns carry the identifying text. No benchmark: `s9-benchmarks` owns it.
verified: `make lint`, `make test` (both exit 0). Exact-string tests in `ui/utils/utils_test.go` (`TestRenderTableFit*`), plus `TestRenderTableFitNeverExceedsTheWidth` sweeping every width 0-45 across each weight shape, wide runes and colour. Green covers the width arithmetic, the CJK cut, the remainder, and that escapes wrap the truncated text; it does not cover anything on screen, since nothing calls this yet.
threads: `runewidth.Truncate` subtracts the tail's width from the budget, so at width 0 it returns a one-cell `…` and overruns the column — `Cell.render` guards width <= 0 for that reason, do not remove it. Cell.Text must be plain: passing pre-coloured text defeats the whole design and mismeasures the column.

### s1-columns (50e891f)

meant: two-column overviews that collapse to one column on narrow terminals and never soft-wrap, spec.md:12.
did: `ui/presentation/columns.go` — `Columns`, `truncateStyled`, `csiPrefixLen`, `minTwoColWidth = 110`. Splits both blocks on newlines, cuts each line to `(width - 2*gap - 1) / 2`, pads the left with `utils.WithPadding`, joins with a `│` rule; stacks below the threshold.
deviations: the ticket says "ANSI-aware measurement via Decolorise", which taken literally means decolorising before the cut and losing the line's colour exactly when it overflows. Implemented as escape-preserving truncation instead (`truncateStyled` copies CSI sequences through, counts only visible cells, closes the cut with a reset) — measurement is still Decolorise-based, the colour just survives. `gap` is defined as the blank cells on EACH side of the rule, so the rule consumes `2*gap + 1`; the ticket did not say which. Two policies it did not specify: an empty right block returns the left block untouched, and a gap wide enough to leave no column falls back to stacked instead of emitting negative padding. Width is counted per rune, not per grapheme cluster, so a combining mark would be double-counted — noted in the comment, no AWS identifier carries one. No benchmark: `s9-benchmarks` owns it.
verified: `make lint`, `make test` (both exit 0). `columns_test.go` covers ragged heights, coloured measurement, the narrow fallback and the threshold itself, empty blocks, plain and coloured truncation, plus `truncateStyled`/`csiPrefixLen` directly, and `TestColumnsNeverExceedsTheWidth` sweeps every width up to 260 across four gaps. Green proves the string arithmetic; it proves nothing about how 110 looks on a real terminal.
threads: `minTwoColWidth = 110` is a starting guess to be tuned by eye, so the tests deliberately use width 200 and only the threshold test references the constant — tuning it must not rewrite every expectation. `csiPrefixLen` handles CSI only, matching what `utils.Decolorise`'s regexp matches and what fatih/color emits; an OSC sequence would be counted as text.
